# ytamp — Code Review, 2026-09-09

**Scope:** every file under `src/`, the docs, the build and CI setup, and the
`crmne/fastpotify` source the skin engine was ported from. Verified by
building, running the test suite, clippy, fmt, the `audio-alsa` build, the
live InnerTube tests, and a live playback probe against YouTube from an ordinary home connection.

**Verdict:** the architecture is sound and the skin engine port is faithful,
but the app as merged on `integration` could not play a single YouTube track.
Three independent bugs sat between the resolver and the decoder; all three
are fixed on the `fix/native-playback` branch, and a track now resolves,
decodes, plays, and seeks end to end. Beyond that, the README's default build
is silent by design, cookies never reach the player, and several mini-player
controls are wired to do nothing. The list below is ordered by impact.

## Blockers, fixed on `fix/native-playback`

1. **The mp4 demuxer rejected every stream.** symphonia's isomp4 reader
   requires `byte_len()` when a source says it is seekable, and the
   `MediaInputStream` wrapper in `src/audio/decode.rs` hardcoded `None`.
   Every YouTube track failed at probe time with "stream is not seekable".
   The WAV tests passed because the WAV demuxer never asks. Fix: `MediaInput`
   is now symphonia's `MediaSource`, and `RangedHttpSource::open` fetches the
   first slice up front so `Content-Range` gives the length before probing.
2. **Player requests carried no visitor id.** Without `X-Goog-Visitor-Id`
   and `context.client.visitorData`, `android_vr`, `tv`, and `visionos` all
   answer `LOGIN_REQUIRED` ("Sign in to confirm you're not a bot"), even from
   an ordinary home connection. The client now mints one from the InnerTube
   `visitor_id` endpoint and caches it for an hour. `Origin` is now sent on
   every call.
3. **The client chain was already stale.** yt-dlp 2026.08.19 marks
   `android_vr` and `ios` as PO-token clients. Their URLs serve only ranges
   that end within roughly the first megabyte; anything later returns 403
   or a redirect that 403s. The one token-free client today is `VISIONOS`,
   now first in the anonymous chain. The research in `docs/02` predates this
   change.

The silent fall-through made all three invisible: the resolver dropped to the
system `yt-dlp` (2025.12.08, which picks the equally truncated `ANDROID`
URL), and the first error a user would see was an HTTP 403 mid-probe. The
resolver now logs why each native client failed, and
`cargo run --example probe` plays and seeks a track through the real engine
for the next time YouTube moves.

## Critical, still open

4. **The README's build is silent.** `cargo run --release` builds without
   `audio-alsa`, so the engine plays into a realtime-paced null sink. The user
   sees position and spectrum move and hears nothing. Either make
   `audio-alsa` default (the feature exists only because the build server
   lacked ALSA headers) or put the flag in the README. CI installs
   `libasound2-dev` and then never compiles the device sink.
5. **Cookies never reach the player.** `YtampApp::new` calls
   `PlayerEngine::spawn`, which builds an anonymous `YtClient`; the
   cookie-armed client is created afterwards and used only for search and
   radio. `set_cookie_path` rebuilds the search client and the engine keeps
   the old one. The Premium 256 kbps lane the README advertises is
   unreachable. Also, even with cookies plumbed, web-family InnerTube calls
   need the `Authorization: SAPISIDHASH …` and `X-Origin` headers yt-dlp
   builds in `_generate_cookie_auth_headers`; without them the cookies are
   ignored.
6. **The playlist window toggle cancels itself.** `windows_buttons` flips
   `state.playlist_open` and calls `host.toggle_playlist_window()`; after the
   draw `frame_mini` flips `mini.winamp.playlist_open` again. Net effect: the
   PL button, and the playlist's own close button, do nothing. The EQ path
   survives only because the app keeps a separate `eq_open` and copies it in
   before each draw.
7. **The built-in skin is a blank grey slab, rebuilt every frame.**
   `Skin::builtin()` generates flat sheets (no drawn buttons, digits, or
   font, so the marquee and clock are invisible) and `frame_mini` calls it
   every frame with a fresh id, so `SkinTextures::get` discards and
   re-uploads every sheet each frame. Cache one `Arc<Skin>` in `MiniState`,
   and bundle fastpotify's drawn `assets/skins/fastpotify.wsz` (MIT) as the
   built-in.
8. **Thumbnails never load.** `egui_extras` is built with `image` only; the
   `Image::new("https://…")` rows in `ui/search.rs` need the `http` feature
   (`ehttp` loader). The `cache/` directory from DESIGN.md is created and
   never used.
9. **The device sink has a real race.** `RodioSink` talks to one global
   device thread with untargeted `Stop`/`Pause`/`Play`/`SetVolume` commands.
   On `Next`, the new session opens its sink while the old decode thread may
   still be blocked in a range fetch; when it finally exits, its `Drop` sends
   `Stop`, which stops the new sink. Tag commands with a sink id. Separately,
   `LiveSource::next` takes a `Mutex` per sample on the audio callback
   thread (88 200 locks per second, contended by the decoder's `extend`);
   use a lock-free SPSC ring and pop in batches.
10. **`NullSink` fast-forwards after a pause.** Pacing is computed from
    total samples since the first write; `pause()` is a no-op, so on resume
    it writes without sleeping until it "catches up", jumping the position
    by the pause length. This is the sink the default build uses.

## Important

11. **Startup downloads the whole file before the first sample.** The trace
    shows seven sequential 512 KiB fetches (the entire 3.6 MB) during the
    demuxer's atom scan, then a seek back to 0. A seek later refetches
    chunks it already had. Keep fetched ranges in a `BTreeMap` (a song is a
    few MB) and the scan, playback, and seeks stop paying twice.
12. **Volume is re-sent every packet.** `EngineCtl::pre_packet` calls
    `sink.set_volume` on every packet; for `RodioSink` that is a channel
    message every ~23 ms. Send on change.
13. **Stop means two different things.** The main window sends
    `PlayerCommand::Stop` (clears the track). The mini player sends
    `PlayPause` + `SeekRatio(0)` so the track stays loaded, but the seek is
    only applied when the decode loop runs, and while paused the loop is
    parked, so `position_secs` stays where it was and `stopped()` (which
    checks `position == 0.0`) reports "paused": the clock blinks the old time.
14. **Decorative controls.** Shuffle and repeat toggle lamps only; the engine
    has no shuffle or repeat. Balance previews in the marquee and sends
    nothing. The `A` (always on top) lamp does nothing. The kHz readout is a
    hard-coded " 44". Either wire them or disable the sprites.
15. **Dropped skins install twice in mini mode.** `winamp_ui` forwards
    dropped files through `host.load_skin_file`, and `frame_ui` also runs
    `handle_dropped_skins`: two copies, two toasts.
16. **Two EQ implementations.** `src/eq.rs` (fastpotify's `EqProcessor`,
    presets, response curve) and `src/audio/mod.rs` (a second
    `EqProcessor` over `EqSpec`) carry the same biquad, `band_widths`,
    `chain`, and `solve` code. The engine uses the second; the UI uses the
    first's presets and curve. Keep one DSP and have the UI import it. Two
    unrelated `Analyser` types (`vis::Analyser`, `audio::analyser::Analyser`)
    invite the same confusion.
17. **The yt-dlp fallback ignores cookies and version.** It never passes
    `--cookies`, so a Premium user's fallback is anonymous, and it trusts
    whatever `yt-dlp` is on PATH. The 2025.12.08 binary on this machine
    produced a truncated URL; 2026.08.19 works. Log the version, pass the
    cookie file, and tell the user in the toast when the binary is old.
18. **Skin loader regressions vs fastpotify.** Folder skins no longer search
    nested directories and no longer refuse symlinks; fastpotify's tests for
    both were deleted rather than ported. `.wal` files are listed as skins
    in the library but always fail to load.
19. **Two tokio runtimes plus a device thread plus decode threads.** The app
    runtime (search) and the engine runtime could be one. Not a bug, but the
    `PlayerEngine::Drop` three-second spin-wait exists because decode threads
    can be blocked in `block_on` against the runtime being dropped.

## Housekeeping

20. `BUILD.md` is linked from the README and does not exist.
21. The README lists "likes-later", "your library", and Premium streams as
    features; none is implemented. Status says "early alpha", which is right.
22. `docs/PLAN.md` still shows Phase 2 unchecked although the merge is done,
    and `docs/02` should note that `android_vr` now needs a PO token.
23. `install_fonts` hunts the filesystem for Inter while
    `assets/fonts/InterVariable.ttf` is already bundled for the pixel text.
24. `main.rs` re-enters `eframe::run_native` in a loop to switch windows.
    fastpotify does the same, so it is presumably fine on winit 0.30, but it
    is untested here and worth a run on both Wayland and X11.

## What is good

- The skin engine, pixel text, playlist, equalizer window, EQ solver, and
  analyser are near-verbatim fastpotify (MIT headers kept), with fastpotify's
  tests kept and three real skins added as fixtures. This is the hard part
  and it is done well.
- The engine's generation-counter sessions are a clean way to make
  Next/Stop/queue-replace safe without locks in the decode loop, and the
  `SessionCtl` seam lets the WAV tests drive the real loop offline.
- Search and radio parsing are tested against captured InnerTube responses,
  not hand-written JSON.
- Settings are atomic-write JSON with `serde(default)`, mirroring fastpotify.

## Account sign-in and the library

There is no official YouTube Music API. The two real options:

- **Cookies (what the code half-implements).** Export a Netscape cookie
  file from an incognito YouTube Music session. With the SAPISIDHASH header
  the same InnerTube `browse` endpoints the web app uses return liked songs
  (`FEmusic_liked_videos`), playlists (`FEmusic_liked_playlists`), library
  songs, albums, artists, history, and uploads. Premium accounts also skip
  the PO-token requirement on `web_music`, which is the 256 kbps lane.
  Durable, and what ytmusicapi, youtui, and limusic all lean on.
- **OAuth "TV and limited input" device flow** with a Google Cloud OAuth
  client the user creates. Google killed yt-dlp's built-in variant, but
  youtui/ytmapi-rs still ship it as of August 2026. Nicer than cookies,
  one policy change from death.

The official YouTube Data API v3 (proper OAuth) exposes YouTube playlists
and the "Liked videos" playlist, but not YouTube Music's library, and it
cannot stream audio, so it is at most a supplement.

For the data layer, `ytmapi-rs` (crates.io, the youtui project, ~40 YT
Music endpoints, cookie and OAuth auth, released 2026-08) already
implements all of this; decision D3 in PLAN.md chose a thin own client and
noted ytmapi-rs as re-evaluable for library sync. Given how much of the
InnerTube surface the library needs, taking the dependency is the faster
path.
